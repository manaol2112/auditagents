# Back-end security

The engine and its API hold confidential client audit records for several clients: uploaded RCMs, extracted controls, plans, review findings, and the decisions people make on them. This file is the record of the back end's controls, in the same form as `web/SECURITY.md` (threat, control, where, tested by), plus the gaps still open. Keep it current when a control changes.

## Threats and controls

| Threat | Control | Where | Tested by |
|---|---|---|---|
| One client's data reaching another client's team | Engagement membership checked on every engagement-scoped request; uploads, intake findings, contradictions, review findings, identity issues, and jobs are resolved to their engagement first; deny by default; the engagement list and the client list are filtered by membership | `src/api.ts` `scopeOf` and the `onRequest` hook, `src/auth.ts` `isMember` / `canSeeClient`, `src/workspace.ts` `listEngagements` | `test/api.test.ts` "isolation between clients and engagements" |
| Learning that another client's engagement exists | A record the user may not see answers exactly like one that does not exist (`404 not found`, fixed body) | `src/api.ts` `NOT_FOUND` | `test/api.test.ts` (same 404 for a missing and a forbidden engagement) |
| Unauthenticated access | Every `/api` route except sign-in needs a session; an `/api` path that matches no route is refused before any handler runs (a handler's own path pattern may be looser than the route table) | `src/api.ts` `ROUTES`, `onRequest` | `test/api.test.ts`, `test/workspace.test.ts` "refuses API reads without a session" |
| Session theft through page scripts (XSS) | The browser session is an `HttpOnly; SameSite=Strict; Path=/api` cookie (`Secure` over HTTPS); the token is never in a response body for browsers | `src/api.ts` `sessionCookie`, `POST /api/session` | `test/api.test.ts` "HttpOnly SameSite=Strict cookie, not the token" |
| Cross-site request forgery | Every cookie-authenticated write must carry the session's CSRF token (`X-CSRF-Token`, stored hashed, compared in constant time); plus SameSite=Strict and the Fetch Metadata refusal of cross-site requests in `src/security.ts`; bearer tokens are never sent by a browser on its own | `src/auth.ts` `authenticate`, `src/api.ts` | `test/api.test.ts` (write without / with a forged / with the real CSRF token) |
| Password guessing | scrypt (N=16384, r=8, p=1, 64-byte key, per-user salt); constant-time comparison; the same work and message for unknown users; 5 failures in 5 minutes lock the name; passwords at least 12 characters; never taken on the command line | `src/auth.ts` | `test/api.test.ts` "same message", "locks a user name" |
| Excessive power in one account | The administrator manages people and access but cannot prepare or approve audit work; no administrator can change their own role or retire their own account; a role change or retirement ends the user's sessions at once; retired accounts keep their history but cannot sign in | `src/auth.ts` `hasRole`, `changeRole`, `disableUser`, `src/api.ts` | `test/api.test.ts` "administration" |
| An administrator reading client data | Administration endpoints return names and memberships only; an administrator reads engagement content only as a member, like a reader | `src/api.ts` `/api/admin/engagements`, membership hook | `test/api.test.ts` "sees its content only as a member" |
| Stolen session tokens in the database | Only the SHA-256 of tokens and CSRF tokens is stored; sessions end after 12 hours idle and on password change | `src/auth.ts`, `migrations/003` | `test/api.test.ts` (sign-out ends the session) |
| An agent, or a user acting as another, taking a decision | Agents have no password and cannot sign in; the API acts only as the signed-in user, never a name from the request; the engine's role rules apply (an approver cannot approve a plan they generated; preparers cannot decide) | `src/auth.ts`, `src/api.ts` `need`, engine | `test/api.test.ts` "approval rules hold", "signed-in user is the actor" |
| Tampering with uploaded files, extracted records, or decisions | Database triggers make uploads, their rows, confirmed mappings, extracted records, intake findings (except a one-time human decision), reviews, findings, proposals, and approved plans immutable; every action is in the hash-chained audit trail | `migrations/001`, `migrations/003` | `test/rcm.test.ts` "immutable", `test/mvp.test.ts` |
| A forked audit chain under concurrent writes | Every event insert locks the chain-head row until its transaction commits; every API write runs in one transaction | `src/audit.ts` `recordEvent`, `src/db.ts` `tx` | `test/api.test.ts` "audit chain intact under concurrent writes" |
| Decompression bombs and oversized uploads | 20 MB request limit on the upload route only (1 KB elsewhere, 512 KB for JSON bodies); the ZIP central directory is read before anything is inflated and refused above 200 MB uncompressed, 2,000 parts, or ZIP64; 50,000 rows; cells cut at Excel's limit | `src/rcm/parse.ts` `checkZip`, `src/api.ts` | `test/rcm.test.ts` "decompression bombs", `test/api.test.ts` "over 20 MB" |
| Active content in uploaded workbooks | Files are data: only cell values are read; formulas contribute their cached result and are never evaluated; macros (.xlsm) and legacy .xls are refused; comments are stripped before parsing | `src/rcm/parse.ts` | `test/rcm.test.ts` |
| Prompt injection through client documents | Client text reaches the model only as data inside fixed prompts that say so; every model answer is verified by the engine (citations against the stored lines, field keys against the catalogue, confident columns never overridden); nothing a model returns is used before a person confirms | `src/rcm/mappingAgent.ts`, `src/proposerModel.ts`, `src/reviewerModel.ts` | `test/rcm.test.ts` "mapping agent fills only open columns", `test/model-proposer.test.ts` |
| Error messages leaking internals or echoing input | Engine refusals are user-facing sentences written by the engine; 404s are a fixed body; 5xx bodies are fixed (`src/security.ts`); job failures show the engine's message or "see the server log" | `src/api.ts` `send`, `src/jobs.ts` | `test/api.test.ts` "never echoes input" |
| Path tricks | Uploaded file names are reduced to a base name and never used as a path; the original bytes are stored in the database, not on disk | `src/rcm/upload.ts` | `test/rcm.test.ts` |
| Supply chain | Two new runtime dependencies, pinned exactly (`exceljs` 4.4.0, released 2023-10-19; `jszip` 3.10.2, released 2026-09-08), both older than 14 days at pin time | `package.json` | `npm audit` |

## Known gaps, to close before this is reachable by anyone else

1. **No HTTPS in the stack.** The cookie is `Secure` only over HTTPS (or with `COOKIE_SECURE=1`). Put a TLS-terminating proxy in front (with HSTS) before exposing the server beyond the machine.
2. **No single sign-on or multi-factor authentication.** Local passwords only. Firms will expect SSO (SAML / OIDC) with MFA; the session layer is written so an identity provider can replace `login`.
3. **No email-based password reset.** People change their own password with the current one (`POST /api/me/password`); a forgotten password is reset by an administrator, and that reset is temporary. Passwords are checked against built-in rules but not yet against a list of the most common breached passwords (ASVS V6.2), and there is no reuse history.
4. **Membership is flat within an engagement.** Any member with the preparer role can add and remove members of that engagement; there is no engagement-owner role.
5. **Client data goes to the model provider.** Model planning, review, and the mapping agent send client document text to the Claude API. That needs the client's and the firm's agreement and a data-processing agreement; the mapping agent sends only headers and up to five sample values per open column.
6. **No malware scanning of uploads.** Files are parsed as data and never executed, but they are stored; a scanner should run before a file is offered for download (no download endpoint exists yet).
7. **Jobs run in the API process.** A restart marks unfinished jobs failed; a queue and worker process would isolate model calls from request handling.
8. **No encryption at rest beyond the database's own.** Uploaded files and records are in PostgreSQL; use encrypted storage for the volume, and encrypted backups.
9. **Rate limits cover sign-in only.** Add per-user limits on uploads and model jobs (cost and denial-of-service).
